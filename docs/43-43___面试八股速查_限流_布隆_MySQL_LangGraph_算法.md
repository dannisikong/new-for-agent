# 模块一 · 分布式限流（面经第 6 题）

## 1.1 四种算法原理与对比

| 算法 | 原理一句话 | 流量特征 | 突发能力 | 实现成本 | 典型场景 |
|---|---|---|---|---|---|
| 固定窗口 | 按时间窗计数，到点清零 | 实现最简单 | 窗口边界可突刺近 2 倍 | 最低 | 粗粒度配额 |
| **漏桶** | 请求进桶排队，桶以**恒定速率**漏出处理，桶满拒绝 | 出口匀速，削峰填谷 | 不允许突发 | 低（队列 + 固定速率） | 写 DB / 消息队列前缓冲 |
| **令牌桶** | 桶按固定速率生成令牌攒着，请求取到令牌才放行，桶满停加 | 平均速率受控，短时可攒令牌一次性放出 | **允许合理突发** | 低（O(1) 状态 + 惰性填充） | API 网关、用户接口、重试突发 |
| **滑动窗口** | 统计「过去 N 秒内」请求数，窗口随当前时间向前滑、淘汰过期请求 | 任意连续区间都精确限速，最平滑 | 不鼓励突发 | 较高（存时间戳并淘汰） | 精确防刷、防固定窗口边界突刺 |

> 固定窗口是前置铺垫：窗口末尾 30 秒 + 下一窗口开头 30 秒可能放过近 2 倍流量（临界突刺），工程上因此淘汰，引出后三种。

## 1.2 令牌桶状态字段与惰性填充

- `capacity` 桶容量、`rate` 每秒生成速率、`tokens` 当前令牌数、`last_refill_ts` 上次填充时间。
- **惰性填充**：请求来时先按 `now - last_refill` 算应补令牌 `tokens += elapsed × rate`（封顶 `capacity`），再判断 `tokens ≥ 1` 放行并扣减；不需要后台定时器定时刷令牌。

## 1.3 滑动窗口结构体字段（内存版）

- `window_ms` 窗口大小、`limit` 阈值；`timestamps` 有序队列/数组，存每个请求毫秒时间戳（队首最旧）。
- `is_allowed(now)`：① 先把队首 `≤ now - window_ms` 的时间戳全部弹出；② `len(timestamps) < limit` 才把 `now` 入队并放行，否则拒绝。

## 1.4 滑动窗口对比令牌桶的缺点

1. **内存 O(n)**：要存窗口内每个请求时间戳；令牌桶只有两个状态量，O(1)。
2. **操作更重**：要做过期淘汰与有序维护；令牌桶惰性填充是 O(1)，不用遍历历史请求。
3. **分布式更复杂**：要借 Redis + Lua 保证清理、计数、写入原子；令牌桶单机就能用 Guava `RateLimiter` 就地跑。
4. **精度换成本**：简单约束下令牌桶已够用，滑动窗口是为「任意区间都精确」支付更高复杂度。

## 1.5 Redis 实现滑动窗口（标准答案：ZSET + Lua）

- 结构：**Sorted Set 有序集合**，`key = rate:{资源}:{用户/来源ID}`；`member` = 请求唯一标识（时间戳 + 序号），`score` = 毫秒时间戳。
- Lua 脚本原子执行：① `ZREMRANGEBYSCORE` 删除 `0 ~ now-windowMs` 过期成员；② `ZCARD` 取当前窗口计数；③ 小于阈值 `ZADD` 放行，否则拒绝。
- **为什么用 Lua**：Redis 单线程顺序执行 Lua，「清理 → 计数 → 写入」不被插队，避免并发下计数超发；拆成多条命令会有竞态。
- 内存优化：把窗口切成固定时间桶（Hash 分桶计数 + 过期 TTL），比全量存时间戳省内存，适合超大规模限流。

## 1.6 项目结合

本项目 `web_search` 目前只做 `@with_retry` 退避，尚未接限流；上线后可对每个用户/来源 ID 用 **Redis ZSET 滑动窗口**防刷，内部重试等允许突发的场景用**令牌桶**。

# 模块二 · 布隆过滤器（面经第 8 题）

## 2.1 原理

- 底层是一个 **m 位 bit 数组**（初始全 0），配 **k 个相互独立的哈希函数**。
- **写入**：元素经 k 个哈希算出 k 个位置，把这些位全部置 1。
- **查询**：元素同样映射到 k 个位置——只要有 **1 个位是 0 → 一定不存在**；k 个位**全是 1 → 可能存在**（存在误判）。
- 标准布隆**不支持删除**；要删除用计数布隆（Counting Bloom，每位换成小计数器，代价是更占空间）。

## 2.2 优缺点

| 优点 | 缺点 |
|---|---|
| 空间极省：只存比特位、不存元素本体，海量集合内存远小于 Set/哈希表 | 有**假阳性**：没写入的元素可能哈希位恰好全被占成 1，误判为存在 |
| 查询/写入都是 O(k)，k 是常数，速度快 | 标准结构**不支持删除**，计数布隆才支持且更耗空间 |
| 实现简单、可并行，适合常驻内存前置层 | 取不出元素本身、不能遍历集合；误判率随填充率上升 |

## 2.3 误判还是漏判（必考点）

- **只有假阳性（误判「存在」），没有假阴性（漏判「存在」）**：已写入元素的位必然是 1，查询它绝不会被判成不存在。
- 口径：**「判不存在」→ 一定不存在，可信任；「判存在」→ 可能误判，必须回真实存储二次确认。**

## 2.4 检索 / RAG 场景解决什么

1. **防缓存穿透**：对已收录文档标题、chunk ID、索引清单、已缓存问题先建布隆；布隆说不存在就直接短路，请求不打到数据库/向量库。
2. **前置去重**：召回 chunk、历史问题、候选 URL 去重，避免重复召回与重复入库。
3. **项目结合**：`knowledge_search` 可对已入库 `doc_title` 建布隆——布隆直接判不存在时，直接走「知识库未收录」回复，少跑一遍 BM25/向量检索流程。
4. **边界提醒**：布隆只能判断「这个 ID/标题是否已收录」，**不能判断语义相关性**；相关度仍交给 BM25、向量检索和 rerank；误判场景必须以后端真实查询为准。

> 对比一句话：Set 精确但吃内存；布隆用「可接受的误判」换海量数据下的内存与速度，是空间换时间 + 精度换空间的取舍。

# 模块三 · MySQL（面经第 9–13 题）

## 3.1 索引失效场景（B+Tree / InnoDB）

1. **索引列上做函数、运算、类型转换**：`WHERE YEAR(create_time)='2026'`、`WHERE age + 1 = 10`；隐式类型转换（字符串列 `phone` 写成 `WHERE phone = 13800000000`）。
2. **联合索引不满足最左前缀**：索引 `(a,b,c)`，只查 `b` 或只查 `c` 都不走索引。
3. **前导模糊**：`LIKE '%abc'`、`LIKE '%abc%'`。
4. **`OR` 两侧有非索引列**：`WHERE a=1 OR d=2`，`d` 无索引导致整体放弃；两侧都有索引时才可能走 index merge。
5. **过滤范围过宽/区分度低**：`!=`、`<>`、`NOT IN`、`IS NOT NULL`，或性别这类少量取值列，优化器估算全表更便宜而放弃索引。
6. **隐式字符集/排序规则不一致**：关联表两列字符集不同导致转换失效。
7. **联合索引范围列右侧失效**：`(a,b,c)` 中 `a` 用范围查询，`b、c` 无法继续用索引（范围列放最右原则）。
8. **表很小 / 返回行占比过高**（经验阈值约 20%–30%）：优化器认为回表成本高于全表扫描。

## 3.2 `LIKE` 何时走索引

| 写法 | 是否走索引 | 原因 |
|---|---|---|
| `LIKE 'abc%'`（右模糊/前缀匹配） | **走索引** | B+Tree 按值有序，能定位 `abc` 前缀区间 |
| `LIKE '%abc'`（左模糊） | 失效，全表扫 | 无法利用有序性定位起点 |
| `LIKE '%abc%'`（双模糊） | 失效，全表扫 | 两端都不确定 |

补救：左模糊用 **FULLTEXT 全文索引**、搜索引擎（ES）；或把字符串**反转后建索引**，匹配 `%abc` 转成查 `cba%` 走右模糊。

## 3.3 事务隔离级别与三大问题

| 级别 | 脏读 | 不可重复读 | 幻读 | 说明 |
|---|---|---|---|---|
| READ UNCOMMITTED 读未提交 | 有 | 有 | 有 | 读到未提交数据 |
| READ COMMITTED 读提交（RC） | **解决** | 有 | 有 | Oracle/PG 默认；MySQL 非默认 |
| REPEATABLE READ 可重复读（RR） | 解决 | **解决** | 基本解决 | **MySQL InnoDB 默认**；MVCC + next-key 锁防范围插入 |
| SERIALIZABLE 串行化 | 解决 | 解决 | 解决 | 全程加锁，并发最差 |

三大问题定义：

- **脏读**：读到别的事务**未提交**的修改，对方回滚后读到的就是脏数据。
- **不可重复读**：同一事务内两次读同一行，中间被其他事务**提交修改**，两次结果不同（侧重 UPDATE 改行内容）。
- **幻读**：同一事务两次范围查询，中间其他事务**提交插入/删除**符合条件的行，两次返回集合行数不同（侧重 INSERT/DELETE）。

## 3.4 MVCC 详解（多版本并发控制）

**目标**：读写不互相阻塞，用历史版本支撑快照读，提升并发。

**三个组成部分**：

1. 每行两个隐藏列：`trx_id`（最近修改该行的事务 ID）、`roll_pointer`（指向 undo log 上一版本）。
2. **undo log 版本链**：同一行被多次修改，沿 `roll_pointer` 串起历史版本。
3. **Read View 一致性视图**：查询瞬间生成，含 `m_ids`（当时活跃未提交事务 ID 列表）、`min_trx_id`、`max_trx_id`、`creator_trx_id`。

**版本可见性规则**（沿版本链回溯）：

1. `trx_id == creator_trx_id`：自己改的，**可见**。
2. `trx_id < min_trx_id`：生成视图前已提交，**可见**。
3. `trx_id ≥ max_trx_id`：视图生成后才开始的事务，**不可见**。
4. `min_trx_id ≤ trx_id < max_trx_id`：在 `m_ids` 中（仍活跃）→ 不可见；不在 `m_ids`（已提交）→ 可见。
5. 当前版本不可见就沿 `roll_pointer` 找上一可见版本。

**RC 与 RR 的关键区别**：

- **RC**：**每次 SELECT 都生成新 Read View**，所以能读到别人新提交 → 不可重复读。
- **RR**：事务**第一次快照读时生成一个 Read View 并全程复用** → 重复读同一快照。

**Read View 并发场景（口述四个）**：

- **场景 A（RR 复用视图）**：T1 开启后第一次 SELECT 生成 Read View；T2 随后提交某行修改；T1 第二次 SELECT 复用旧视图，看不到 T2 的提交 → 可重复读。
- **场景 B（RC 每次新视图）**：同一时序，RC 第二次 SELECT 生成新视图，能看到 T2 已提交 → 出现不可重复读。
- **场景 C（自己可见）**：T1 改完行再读，版本 `trx_id == creator_trx_id`，自己的版本可见。
- **场景 D（历史版本回溯）**：视图前已提交版本可见；视图后启动事务的版本不可见，沿版本链找到对自己可见的旧版本。

> 补充：**快照读**（普通 SELECT）走 MVCC；**当前读**（`SELECT ... FOR UPDATE`、`LOCK IN SHARE MODE`、`UPDATE`、`DELETE`、`INSERT`）读最新版本并加锁，不走快照。

## 3.5 行锁 / 表锁 / 间隙锁触发时机

| 锁类型 | 作用对象 | 触发时机 |
|---|---|---|
| **表锁** | 整张表 | `LOCK TABLES READ/WRITE` 显式加锁；DDL 变更；更新条件**没走索引**时扫全表逐行加锁，效果退化为表级阻塞 |
| **意向锁（IS/IX）** | 表级协调层 | 事务想加行锁前先加意向锁，快速判断表上是否存在冲突锁，本身不阻塞业务并发 |
| **记录锁 Record Lock** | 单条索引记录 | 等值命中**唯一索引**，对该行加 X 锁（`UPDATE/DELETE/SELECT FOR UPDATE`） |
| **间隙锁 Gap Lock** | 两条索引记录之间的空隙 | RR 下范围查询、阻止其他事务在空隙插入；多个事务可同时持有同一间隙的 Gap Lock（不互斥） |
| **Next-Key Lock** | 记录锁 + 间隙锁 | RR 默认行锁单位：锁住记录及其前方间隙；范围查询、普通索引等值、唯一索引等值未命中时触发，用来防幻读 |

**一句话收尾**：InnoDB 行锁建立在索引上，**没有索引的写操作会退化成扫全表加锁**，所以高并发更新一定要给过滤条件建索引；RR 下用 next-key lock 同时解决不可重复读和范围幻读。

# 模块四 · LangGraph Reducer 与多 Agent 协作（面经第 15、16 题）

## 4.1 Reducer 机制怎么用

- **Reducer = 字段级合并规则**：LangGraph 状态（`StateGraph` 的 `TypedDict`）每个字段用 `Annotated[类型, reducer函数]` 标注，定义多个节点返回 partial state 时**如何合并进全局状态**，而不是整体覆盖。
- **不写 reducer**：节点返回的该字段直接**整体覆盖**旧值。
- **内置 `add_messages`**：消息字段按 `id` 合并——同 id 更新、不同 id 追加；本项目 `RAGState.messages`、`AgentState.messages` 都用它：

```python
messages: Annotated[list[AnyMessage], add_messages]
```

- **自定义 reducer**：列表追加 `lambda old, new: old + new`、字典按 key 合并、计数器累加、集合取并集；节点本身只产出增量，合并逻辑收口到 reducer。

## 4.2 并发下状态冲突怎么解决

| 情况 | 处理方式 |
|---|---|
| 并行节点写**同一字段** | 必须配 reducer，按追加/累加/按 key 合并语义合并，避免后写覆盖先写 |
| 并行节点各写**不同字段** | 职责隔离，天然无冲突，优先采用这种设计 |
| 读-改-写同一列表/计数器 | 由 reducer 承担合并语义；需要去重/排序在 reducer 内完成 |
| 字段有**数据依赖**（B 要 A 的输出） | 走条件边串行，不 fan-out |

**设计三原则**：① 并行写同字段就上 reducer，不并行就让节点各写各的字段；② 依赖关系在边上表达清楚；③ 复杂冲突（去重、加锁、资源争用）收口到 reducer 或汇总节点，不在业务节点里抢写。

> 对照本项目：`messages` 用 `add_messages` 合并工具回环消息；`trace` 列表是节点内「读旧列表 + 新项」再整体返回，靠串行边保证一致；**若将来把多个检索节点并行化，`trace` 也要换成追加型 reducer**，否则会出现并行覆盖。

## 4.3 多 Agent 之间的通信方式

| 模式 | 机制 | 适用 |
|---|---|---|
| **Supervisor 主管** | 中央 Agent 分发任务给 worker，worker 回传结果，supervisor 决定下一步 | 分工明确、需要统一仲裁 |
| **层级委派 / Handoff** | Agent 通过 `Command(goto="worker", update={...})` 移交控制权和状态 | 任务链条长、上下文要交接 |
| **共享黑板 / 共享 state** | 所有 Agent 读写同一份状态，靠 reducer 合并产出 | 松散协作、结果汇总类 |
| **显式消息通道** | Agent 间按 topic/收件人发消息，状态只留必要上下文 | 解耦、事件驱动协作 |
| **工具集隔离** | 每个 Agent 绑定自己的工具，不互调内部方法，只通过消息/结果协作 | 控制耦合与权限边界 |

## 4.4 任务拆分出现依赖冲突怎么处理

1. **先画 DAG**：识别数据依赖——有依赖的节点串行，无依赖的才并行 fan-out。
2. **字段归属表**：明确谁读、谁写、谁聚合；并行阶段各写独立字段，汇总节点用 reducer 合并。
3. **资源冲突**：多个 Agent 写同一外部系统/文件 → 加锁、排队串行，或各自产出副本由汇总节点合并。
4. **循环等待/优先级冲突**：由 supervisor 统一仲裁排队，不让 worker 之间互相死等。
5. **兜底**：checkpointer 保存状态做断点恢复；冲突决策走人在回路 `interrupt`；子图隔离上下文边界，避免状态污染。

## 4.5 结合本项目讲（面试可直接说）

- 现状：`agentic_rag` 是**单 Agent 状态机**：`decide → rewrite_query → retrieve → grade → rewrite/web_search → confirm → answer`，消息靠 `add_messages` 合并，轨迹列表串行拼接。
- 演进到多 Agent 的方案：**supervisor（规划）+ retriever Agent（BM25/向量）+ web Agent（联网）+ answerer Agent**；共享 state 用 reducer 合并各 Agent 的证据片段；supervisor 用条件边做 handoff；**检索与联网无依赖可并行**，answer 节点必须等两者结果（依赖串行）；冲突字段（证据列表）由 reducer 去重合并。

# 模块五 · 链表 / 哈希算法口述（面经第 17 题）

## 5.1 口述通用套路

1. **复述题意 + 确认约束**：链表是否为空、是否带头节点、值范围；哈希题确认返回索引还是元素。
2. **先说选型与复杂度**：快慢指针 / 哨兵节点 / 哈希表，报出时间 O(n)、空间 O(1) 或 O(n)。
3. **讲步骤**：指针初始化 → 循环条件 → 每步怎么移动 → 收尾边界。
4. **报边界 case**：空链表、单节点、删头节点、环、重复值、进位溢出。
5. **口述代码骨架**：变量名 + 核心 3–5 行，不默写全代码。

## 5.2 链表高频题

| 题目 | 思路一句话 | 复杂度 | 口述要点 |
|---|---|---|---|
| **反转单链表**（206） | 迭代三指针 `prev / curr / next`，边遍历边改指向 | O(n) / O(1) | `next=curr.next` 存后继 → `curr.next=prev` → `prev=curr` → `curr=next`；递归是先走到尾再反向回溯 |
| **判断有环**（141） | 快慢指针，快 2 步、慢 1 步，相遇即有环 | O(n) / O(1) | 快指针走不动（null）说明无环；相遇不代表入口 |
| **找环入口**（142） | 相遇后一指针移到表头，两指针同速走，再相遇即入口 | O(n) / O(1) | 头到入口距离 = 相遇点到入口距离；要讲得出为什么 |
| **合并有序链表**（21） | 哨兵 `dummy` + 双指针比小的接入尾 | O(n+m) / O(1) | 谁小接谁、对应指针后移，最后把剩余链表整段接上 |
| **删倒数第 N 个**（19） | 快指针先走 N 步，再与慢指针同速，快到末尾删慢的后继 | O(n) / O(1) | 哨兵节点解决删头节点；慢指针停在待删节点前驱 |
| **回文链表**（234） | 快慢找中点 → 后半段反转 → 双指针比对 | O(n) / O(1) | 偶数节点中点靠右；比对到后半段结束 |
| **两数相加**（2） | 哨兵节点 + `carry` 进位，逐位相加 | O(max(m,n)) / O(1) | 两链表都走完还要处理最后 `carry=1` 新建节点 |

## 5.3 哈希高频题

| 题目 | 思路一句话 | 复杂度 | 口述要点 |
|---|---|---|---|
| **两数之和**（1） | 一遍遍历，哈希表存 `值→索引`，查 `target - 当前值` | O(n) / O(n) | 先查表再写入，避免自己配对自己 |
| **异位词分组**（49） | 排序串（或 26 字母计数数组）作 key，哈希表聚合 | O(n·k log k) / O(n·k) | 计数数组序列化做 key 比排序更快 |
| **最长无重复子串**（3） | 滑动窗口 + 哈希表记字符最新位置 | O(n) / O(字符集) | 遇重复字符，左边界跳到「上次位置+1」，右边界一直右移 |
| **多数元素**（169） | 哈希计数；进阶摩尔投票 | O(n) / O(n)（投票 O(1)） | 摩尔投票：候选 + 票数，不同就抵消，最后剩候选 |
| **存在重复**（217 / 219） | 哈希集合判重；219 记上次索引判断 `j-i ≤ k` | O(n) / O(n) | 219 用哈希表存最新索引，旧位置可覆盖 |
| **LRU 缓存**（146） | **哈希表 + 双向链表**：定位节点 O(1)，移到队首/删队尾 O(1) | get / put 均 O(1) | 访问即最近使用移到队首；容量满删链表尾；双向链表才能 O(1) 删任意节点 |

## 5.4 和本项目直接呼应（面试加分点）

- 项目 `agentic_rag._answer_cache` 就是一个 **LRU**：用 `OrderedDict` 实现——`move_to_end(key)` 标记最近使用，超容量 `popitem(last=False)` 淘汰最久未用，容量 100。
- 口述 LRU 时对照：`OrderedDict` 底层等价于哈希表 + 链表；手写 146 题时哈希表解决 O(1) 定位、双向链表解决 O(1) 移动/淘汰，二者职责和项目缓存一一对应。
- 工具调用轨迹、会话消息合并用到 `add_messages`（对应模块四 reducer），不是算法题但能体现工程结合。
