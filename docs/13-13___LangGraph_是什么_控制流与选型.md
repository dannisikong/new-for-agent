# LangGraph 是什么（控制流与选型）

**一句话总述：**LangGraph 是 LangChain 开发的框架，专门**管理集成 LLM 应用的控制流**。当应用需要"可预测、可控"的执行流程时，它是正确选择；其核心是用有向图（节点+边+状态）定义应用流程。

## 一、LangGraph vs LangChain

这两个名字容易混淆，它们的关系是：

- **LangChain：**提供与模型和其他组件交互的**标准接口**，适用于检索、LLM 调用、工具调用等
- **LangGraph：**管理应用的**控制流（control flow）**

关键点：

- LangGraph 中**可以但不必须**使用 LangChain 的类
- 两个包不同，可以独立使用
- 不过，网上的资源通常把两者结合使用

## 二、什么时候用 LangGraph？控制 vs 自由

设计 AI 应用时，面临一个基本权衡：**控制（Control）vs 自由（Freedom）**。

- **自由：**给 LLM 更多发挥空间，处理意外问题。例如 smolagents 的 Code Agent 很"自由"——单步可调多个工具、甚至自建工具，但**可预测性差、难以控制**
- **控制：**确保可预测的行为，维持护栏（guardrails）

**LangGraph 处于光谱的另一端**：当你需要对 Agent 的执行进行"控制"时，它大放异彩。简单说：

如果应用包含**一系列需要按特定方式编排的步骤**，且在**每个交汇点做决策**——LangGraph 正好提供你需要的结构。

## 三、典型例子：文档问答助手的分支

假设要构建一个能回答文档问题的 LLM 助手：

1. LLM 最擅长理解文本，所以回答前需要把图表、表格等复杂模态转成文本
2. 但这个转换方式**取决于文档类型**！例如：  

   - 图表 → 需要转成文字描述
   - xls 表格 → 需要写代码（转 pandas 并操作）
3. 这就在流程中产生了**分支（branching）**

**注意：**这种分支可以是确定性的（固定规则判断），也可以**由 LLM 输出决定**（非确定性）。两种 LangGraph 都支持。

## 四、LangGraph 擅长的关键场景

| 场景 | 说明 |
|-|-|
| **多步推理过程** | 需要对流程显式控制 |
| **状态持久化** | 应用需要在步骤之间持久保存状态 |
| **确定性逻辑 + AI** | 把确定性规则与 AI 能力结合的系统 |
| **人机协同** | 需要人类介入（human-in-the-loop）的工作流 |
| **复杂智能体架构** | 多个组件协同工作 |

**核心判断：**作为人类，尽量"根据每个动作的输出，设计下一步执行什么"——这时 LangGraph 就是正确的框架。作者评价：LangGraph 是市面上**最接近生产就绪的 Agent 框架**。

## 五、LangGraph 如何工作：有向图

LangGraph 的核心是用**有向图结构**定义应用流程：

- **Nodes（节点）：**单个处理步骤——调用 LLM、使用工具、做决策
- **Edges（边）：**定义步骤之间可能的转换
- **State（状态）：**用户定义，执行时在节点之间传递；决定下一个目标节点时，就看当前状态

这些构建模块会在下一章详细展开。

## 六、为什么不用普通 Python？

你可能会想："用 if-else 不就能实现这些流程吗？" 技术上确实可以，但 LangGraph 相比原生 Python 有额外优势，它提供现成的：

- **状态管理**
- **可视化**
- **日志（traces）**
- **内置人机协同（human-in-the-loop）**

构建复杂系统时，这些工具和抽象能省很多事。

## 七、新手常见误区

- **误区1：把 LangGraph 当 LangChain。**LangChain 是接口层，LangGraph 是控制流层，可独立使用。
- **误区2：以为 LangGraph 不自由。**它是"可控的自由"——用图结构把 LLM 的决策嵌入流程，不是完全僵化。
- **误区3：用 if-else 硬写复杂流程。**状态、可视化、日志、人机协同都要自己造轮子，LangGraph 已内置。

## 八、本节小结

需要"控制"就选 LangGraph：有向图（节点+边+状态）定义流程，支持确定性/非确定性分支、状态持久化、人机协同。这是它区别于 smolagents（自由优先）的核心定位。
