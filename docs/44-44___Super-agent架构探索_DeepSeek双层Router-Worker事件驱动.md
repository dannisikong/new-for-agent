# 44 · DeepSeek Super-agent 架构探索：双层 Router-Worker + 事件驱动

> 来源：DeepSeek Harness 团队，2026-10-31，《Super-agent 设计探索：迈向更自主的 Agent 系统》
> 原文：https://mp.weixin.qq.com/s/zoS7GlReWPhfCjENGxXCdg
> 性质：工程架构思路探讨（非产品功能介绍），是目前中文社区里少见的"生产级多任务 Agent 系统设计"长文。

## 一句话总述

DeepSeek 提出：把 Agent 从"单次手动 Session"里解放出来，做成一个**跨会话保持上下文、并行推进多任务、事件驱动主动行动、云端持久在线**的连续实体——Super-agent；底层用 **Router 层（常驻路由）+ Worker 层（隔离并发执行）** 双层架构，配合事件两级过滤、订阅直通、Inline/Spill 上下文管理、异步 ReAct、存算分离与 Watchdog 自愈，五个模块支撑"连续、高效、主动、持久"四个特征。

---

## 一、为什么需要 Super-agent（问题定义）

现有主流 Agent 以**单 Session** 为基本单位：

- 用户并行推进多项工作时，要手动切换 Session、记住各自上下文；一个人通常只能同时跟 3–5 个活跃 Session。
- 单任务上限取决于模型能力，**多任务上限取决于人的注意力**。
- 在本地单会话 Agent 上叠加 CLI / MCP / 外部连接器做简单扩展，仍有三个硬伤：
  1. 单会话同步阻塞——一个慢工具跑着，新消息进不来；
  2. 多任务上下文互相污染；
  3. 本地设备一休眠/离线，Agent 就停。

> 文章原话："让用户手动管理 Session，在很大程度上是从底层 LLM API 延续下来的设计惯性；**Session 应当是系统的实现细节，而不应是用户的认知负担**。"

### Super-agent 四个基础特征

| 特征 | 含义 | 本项目对照 |
|---|---|---|
| **连续** | 用户在 IM、GitHub 评论等不同信道切换指令，Agent 能理解全局上下文（IM 说方案 A，PR 评论改成 B，它跟着调） | 本项目 app_web.py 单 Streamlit Session，跨信道能力为零 |
| **高效** | 响应快，能并行高质量完成多个复杂任务，不用等上一个命令跑完 | 本项目 `_memory` checkpointer 单图串行，无并发 Worker |
| **主动** | 不等逐条下指令，持续观察环境事件，该出手时出手，不该介入时安静 | 本项目是纯被动问答，无 Trigger 监听 |
| **持久** | 始终在线，接入真实工作环境，异常自动恢复 | 本项目 Streamlit Cloud 一休眠就停，无 Watchdog |

## 三、双层架构：Router 与 Worker 的分工

| 维度 | Router 层 | Worker 层 |
|---|---|---|
| 职责 | 全局序点、任务分派、跨信道记忆、统一对外回复 | 具体任务执行，挂完整工具集 |
| 模型 | 轻量即可（长输入短输出，决策简单） | 最强模型（直接决定代码质量） |
| 是否直接执行任务 | **不执行**（甚至不配 Bash 工具） | 全部执行 |
| 是否直接回用户 | 是，统一出口 | 否，只向 Router 汇报 |
| 上下文 | 全局，跨任务 | 隔离，单任务内 |
| 内部结构 | 可单 Session；规模大可多层过滤/水平 Sharding | 可再拆 Subagent / Agent Team，对 Router 透明 |

### 关键洞察：Router 批处理（Batching）

- 外部事件密集涌入时，上一轮推理期间积压的多条 Trigger 会**自动合并进下一次 LLM 调用**。
- 因为 Router 是"长输入、短输出"，合并后 Prefill 阶段并行计算，**单次请求耗时增长远慢于批大小增长**。
- 实验：Trigger 速率从 1 条/分钟升到 40 条/分钟，平均 batch 从 1.0 升到 2.8，单次请求耗时只从 2.5s 升到 3.9s，**单决定分摊推理时间从 6.4s 降到 1.6s**。
- 结论：当前团队规模下，单常驻 Router Session 够用，不必过早 Sharding 牺牲全局连续性。

### Router 与常见 Agent Team 的区别

- 常见 Agent Team：Team Lead 深入任务细节、规划子任务、高频协调，推理负载重。
- Super-agent Router：**只管任务间高层关联与分派，不介入单任务内部拆解**；子任务内部再怎么拆（Subagent/Team）对 Router 透明。

## 四、事件驱动：四个递进机制

### 4.1 两级事件过滤（Fast Path / Slow Path）

环境事件"高噪音、低触发率"——绝大多数群消息不需要 Agent 介入。

| 层级 | 实现 | 作用 |
|---|---|---|
| 程序层 Fast Path | 确定性代码：事件来源、群组范围、用户/机器人白名单 | 调 LLM 前滤掉大部分无关消息，低延迟低成本 |
| 语义层 Slow Path | LLM 按提示词策略判断候选事件是否该行动 | 自然语言扩展点，随时改提示词/加策略 |

> 类比计算机系统：大模型是灵活但贵的 Slow Path，固化的高频判断是便宜的 Fast Path。

### 4.2 事件路由：订阅与直通（Thread）

- 同一 GitHub PR / IM 话题 / 邮件串下的连续事件 = 一条 **Thread**。
- Router 处理初始事件 → 创建 Worker → Worker 订阅该 Thread。
- 之后两条路径：
  - **已订阅（Fast Path）**：后续事件由程序直通 Worker，不经 Router 转发；
  - **未订阅（Slow Path）**：Router 观测全局，判断并分派新事件。
- Thread 与 Worker 是**多对多**：一个 Worker 可订阅多个 Thread，一个 Thread 可被多个 Worker 订阅；冲突时同 Thread 事件广播给所有订阅者，它们自行发现冲突。

> 实验数据：去掉直通机制后，任务完成时间基本不变，但 Router 决策数 +30%，总读缓存 token 从 2323 万涨到 3177 万（**+37%**）。直通不提速，但显著省 token。

### 4.3 上下文组织：Inline & Spill + 链式召回

把上下文窗口当 **Cache** 管理（借局部性原理）：

| 操作 | 含义 |
|---|---|
| **Inline** | 近期很可能用到的信息直接内联进上下文窗口，省一次工具往返 |
| **Spill** | 超长/低频内容留在窗外，窗口内只留引用/摘要，需要时再调工具读 |

落地三步：
1. 最少信息开始：只给对象 ID + 内容摘要；
2. 局部性逐步 Inline：先附紧密关联对象 ID，再附时空相邻内容（前 50 字、相邻 IM 消息、相邻评论）；
3. 超上限则 Spill：截断保留续读入口。

**链式召回（Chain of Recall）**：Trigger/Thread/Worker 都带唯一 ID，注入时内联下一跳关联对象 ID，底层构成一张引用图；模型从当前消息出发，顺着引用逐步按需展开——"当前消息 → 所在 Thread → 相关 Worker → Worker 关联的另一个 PR Thread"。

> 文章原话："**浪费上下文窗口，就是浪费模型的智能。**"

### 4.4 投机执行（Speculative Execution）

借鉴 CPU 投机执行：结果不确定时先在后台跑，有价值就交付，没价值就丢弃，用额外后台算力换用户等待时间。

- 个人助手：收到会议邀约，后台先核对日程冲突、搜集背景、起草回复草稿，用户过目即可发。
- 研发场景：DeepSeek 内部"静默复现并修复"策略——群里有人反馈问题，Agent 后台先尝试复现并找修复方案，**只有确认问题且找到简单修复后才交付**，否则全程安静。

## 五、全双工交互与多信道输出

### 5.1 异步 ReAct Loop

经典 ReAct：模型 `run()` 一个工具后阻塞等结果，期间新消息进不来。

改造：耗时工具改为 `start()` / `stop()`：
- `start()` 立即返回 "Started"，循环不阻塞；
- 后台工具完成后，结果作为新事件消息投回会话；
- 模型可 `stop()` 主动终止跑太久的命令。

→ 前台对话与后台任务解耦，实现**全双工**。

### 5.2 多信道输出规范

| 信道 | 风格 | 硬性规范（DeepSeek 验证有效） |
|---|---|---|
| IM 即时通讯 | 低打扰、像人类同事 | 只在需要决策/验收时通知，单次回复**不超过 100 词** |
| GitHub/邮件/文档 | 结构化高密度异步交付 | PR 按项目规范写背景/改动/验证；邮件文档结构化摘要 |

## 六、持久在线：存算分离 + 脑手分离 + Watchdog

### 6.1 两层解耦

| 层 | 解耦内容 | 做法 |
|---|---|---|
| 第一层：计算 vs 状态 | Agent Loop 计算无状态化，Session 状态持久化 | 计算放云端无状态弹性容器（可水平扩/重启/替换），状态存数据库 |
| 第二层：计算 vs 执行环境 | Agent Loop 常驻云端，重状态执行环境留在原地 | 端侧部署**不保存会话状态的轻量 daemon**，只执行命令返回结果 |

- 端侧 daemon 方案 = **BYOM（Bring Your Own Machine）**：接入用户日常开发机（上面有未提交修改、本地凭据、内网依赖），不必把环境搬上云、也不必要求用户迁云。
- 与 Anthropic "Decoupling the brain from the hands" 思路一致：harness 无状态，会话日志存 harness 之外，统一接口接执行环境。区别是 Anthropic 讲托管沙箱/VPC，DeepSeek 这里重点是**间歇在线的个人设备**——设备重新上线后，云端 Agent 自动补跑需要它的任务。

### 6.2 Watchdog（外部 Control Loop）

长期运行的 Agent 只靠传统进程存活探测不够，因为很多异常不是进程崩，而是**模型陷入无效循环或偏离目标**。

- 主系统外部配独立 **Watchdog Session**，用定时消息驱动。
- 职责：① 接口报错/状态恢复失败等基础设施故障；② 判断各 Worker 是否有实质进展、方向是否跑偏。
- 发现异常介入修复；外部偶发故障持续复查直到恢复。
- Watchdog 本身是完整工具能力的 Agent，维护者可用自然语言问它故障原因，也能在线改主系统提示词/触发规则。

## 七、消融实验关键数据（7.1 / 7.2）

合成负载：约 300 条消息、约 20 个工作请求，其余是闲聊/跟进/叫停/CI 消息；每种方案跑 5 次。

| 方案 | p50 完成时间 | p95 完成时间 | 说明 |
|---|---|---|---|
| **Super-agent（完整）** | **12.4 min** | **15.7 min** | Router 不执行 + Worker 订阅 Thread |
| Super-agent 去掉直通 | ≈12.4 min | ≈15.7 min | 完成时间不变，但 Router 决策 +30%、token +37% |
| 单 Session + Subagent（中性提示） | — | 29.5 min | 5 次运行一次都没调 Subagent，全在主 Session 被新消息打断 |
| 单 Session + Subagent（提示优先委派） | 略快 | 长尾 | 5 次中 4 次委派，1 次判断"工作很小"自己干 |

**结论**：
- 双层架构在系统层面解决了"靠提示词让模型自己决定分不分工"的不确定性——Router 制度上就不执行任务，Worker 制度上只收订阅 Thread。
- Super-agent 以更多 token 消耗换更短更稳定的完成时间。
- Router 批处理：40 条/分钟时 batch=2.8，单决定分摊 1.6s，未触单 Router 瓶颈。

## 九、新手误区

1. **误区：Super-agent 就是多开几个 Session**。
   错。多开 Session 没有全局 Router 维持连续性，结果割裂、各自回用户造成混乱；关键是"常驻 Router 统一序点 + Worker 上下文隔离 + Thread 订阅路由"的系统设计，不是数量叠加。

2. **误区：Router 应该用最强模型**。
   错。文章实践：Router 只做高层分派，长输入短输出，**轻量模型就够**；强模型留给 Worker（直接决定代码质量）。把贵模型花在分派上是浪费。

3. **误区：事件过滤就是"要不要调 LLM"**。
   不只是。两级过滤里程序层用确定性规则挡掉 90%+ 噪音，语义层 LLM 只判候选；再加上 Thread 订阅直通，大部分事件根本不经过 Router——这是省 token 的关键，不是"每个消息都问模型一遍"。

4. **误区：异步 ReAct 就是并行调多个工具**。
   不完全是。核心是 `start()` 立即返回、前台对话不被后台慢工具阻塞（全双工），同时支持 `stop()` 主动取消；这解决的是"一个慢命令卡住整个会话"的问题，不是简单并发。

5. **误区：持久在线 = 把 Agent 部署到云上**。
   不够。光把 Loop 上云，执行环境（本地代码库、凭据、内网依赖）还在用户机器上就访问不到；必须配端侧无状态 daemon（BYOM），并解决设备间歇上线后补跑任务的问题。

6. **误区：Watchdog 就是进程监控**。
   不够。Agent 的很多异常是"进程活着但模型死循环/跑偏目标"，Watchdog 要盯任务进展本身，而不只是进程存活。

## 十、面试可讲一句话

> "DeepSeek 这篇 Super-agent 把多任务 Agent 系统抽象成双层：常驻轻量 Router 做全局路由和记忆，强模型 Worker 上下文隔离并发执行，事件走'程序快路径过滤 + Thread 订阅直通'路由，上下文当 Cache 做 Inline/Spill 和链式召回，再用异步 ReAct 解全双工、存算分离+端侧 daemon 做 BYOM 持久在线、外部 Watchdog 盯任务跑偏——本质是把操作系统里的进程调度、中断、投机执行、存算分离思想搬到 Agent 系统上。我们项目现在是单 Session ReAct/RAG，要往生产级多任务走，下一步就是引入 Router-Worker 分层和事件 Trigger，而不是继续在单图里堆节点。"

## 十一、延伸阅读与对照

- Anthropic《Decoupling the brain from the hands》：脑手分离、harness 无状态、会话日志外置——本文第 5.2 节的思想同源。
- 本项目现状对照（new-for-agent）：
  - 单 Session：`agentic_rag.build_rag_graph` / `agent_core.build_react_graph` 各一张图，`_memory` checkpointer 串行；
  - 被动问答：无 Trigger 监听、无事件过滤；
  - 无并发 Worker：ReAct 图单 assistant 节点循环；
  - 已有雏形：`tool_policy` 程序层 Fast Path（参数校验挡越权）、`audit_log` trace（可演进为 Watchdog 观测数据源）、`interrupt` 人在回路（对应"人类在关键节点验收"）。
- 可落地的下一步：① 把 `tool_policy.validate` 从单工具参数校验升级为事件级 Fast Path 过滤；② 用 audit_log 的 trace_id/span/duration_ms 做一个简单 Watchdog，检测工具调用是否死循环（同工具短时间重复 N 次告警）。
